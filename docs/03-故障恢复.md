# 故障恢复：USB Burning Tool 100% 后黑屏，以及 TWRP 循环

> **这页记录本项目确实发生过的故障。涉及 eMMC 写入、Bootloader 与硬件短接的部分仅为事故复盘和专业维修参考，不是给所有 E900V21C 的“通用救砖指令”。** 不知道目标扇区和备份来源时，执行写操作可能造成不可恢复的损坏。

## 先判断哪一种故障

| 看到的现象 | 先做什么 | 暂时不要做什么 |
|---|---|---|
| HDMI 无信号，Windows 工具却显示 100% | 检查烧录日志的擦除动作，检查 Bootloader 来源与 WorldCup 枚举 | 不要马上再刷一次通用整包 |
| 开机 Logo → TWRP → 重启 | 核对 `/data`、`/cache`、分区表、Recovery 命令与 BCB | 不要直接改变整个分区表或盲擦 eMMC |
| 烧录工具无法识别 | 确认电源、数据线、OTG 口、USB VID:PID，判断是否进入 WorldCup | 不要关闭驱动签名检查或盲短接主板 |
| Android 启动但 ADB 无法连接 | 先看 HDMI 桌面与本机网口/Wi-Fi 状态，再诊断 ADB 是否授权 | 不要把网络不通当作肯定“刷砖” |
| 工具提示烧录完成但断电后不能开机 | 查看是否仅写了 system/boot、却误擦了 Bootloader 或 env | 不要只凭工具退出码判断系统完整 |

## 案例 A：11 月 11 日首次全量刷机，进入 TWRP 循环

上游通用 `S905L_6.0.1_TWRP.img` 确实通过 Amlogic USB 通道写入，日志显示包括 Bootloader/boot/logo/recovery/system 在内的各分区写入成功；但之后电视实拍进入 TWRP `Running OpenRecoveryScript`，出现：

```text
Could not mount /data and unable to find crypto footer
Failed to mount '/data' (Invalid argument)
Unable to mount storage
```

随后反复重启。原因不能简单归结为“Android 6 肯定不兼容 S905L”；当时已知候选和原机在**分区布局、TWRP recovery 以及 Bootloader**方面存在明显不同。

处理原则：

1. 先确认到底是 TWRP 恢复分区启动、还是 Android 正常 boot 失败导致自动转恢复。
2. 将候选 DTB 分区表与原机分区表逐项比对；不能按网上另一个 1GiB 版的 `/data` / `system` 布局来格式化本机。
3. 对 `/data`、`/cache` 的单独格式化也要以**已验证的目标映射**为前提；不要使用 Erase flash 代替。
4. 在备份不可用、恢复链路不清楚时，先停下来求助，不要无限重刷。

## 案例 B：11 月 15 日定制包写入成功，随后无 HDMI

这次我们已经做了一个 640MiB / P211 的定制 Amlogic IMG，内含：

- 调整后的 Android 6 boot；
- 调整后的 640MiB system；
- 原机 stock recovery；
- 原机 multi-DTB；
- **不含** `bootloader.PARTITION`。

打包内 `aml_sdc_burn.ini` 采用：

```ini
erase_bootloader = 0
erase_flash = 0
reboot = 0
```

但实际 Windows USB Burning Tool 的 GUI 配置后来被读出为：

```ini
[EraseFlash]
Enable=1
[EraseBootLoader]
Enable=1
```

软件日志显示擦除阶段。**这是本项目最值得传播的教训：镜像 INI 不是 Windows GUI 的最终执行权限。** 对这份没有 Bootloader payload 的包进行擦除，会导致“boot/system 写成功，但启动链缺失/错位”。

当时的处理不是反复按 Start，而是先取消两个 GUI 擦除选项、检查原机备份、进入 RAM U-Boot 做**只读诊断**，最后才作严格限定的引导修复。

## 案例 C：11 月 16 日，本机 FIP 修复的可验证证据

### 第一步：证实问题与找回**自己的**原始备份

我们原有一个 **4MiB** 的原机 Bootloader 备份，大小和 SHA256 均有记录：

```text
original bootloader backup:
size:    4194304 bytes
SHA256:  dabe61af2577f4e3733fa14d010616cdec6f69ac598ff25a73f52e0c9b941cd6
```

读取备份的十六进制结构后确认：文件最前 512 字节是 0，`@AML` 标识位于偏移 528，实际有用的 FIP 范围可截取为从偏移 512 开始的 **917504 字节（896KiB）**。

**这个结论只针对当时这份备份。** 别把 896KiB 生搬硬套给所有 AML 盒子。

### 第二步：读取现有引导，确认写入对象

通过 Windows 的 USB WorldCup 通道和临时 RAM U-Boot，在**不执行擦除**的条件下：

- 使用工具的命名分区读取与哈希，比对发现当前有效 FIP 确实是**通用 Android6 候选包的 768KiB FIP**，不是原厂 FIP；
- 先将当前通用 FIP 单独保存，提供回滚和事故鉴定证据；
- 核对 eMMC 用户区 LBA1 的引导定位资料、备份实际字节结构、目标分区对应关系；
- 确认本次拟写入对象**只限 bootloader/FIP**，不附带 `disk_initial`、`erase_bootloader`、`saveenv`、DTB、system、recovery、data、efuse 等操作。

初期曾因一次性读取尺寸过大，得到了**全零的误导性输出**；改为正确的 FIP 长度后才发现原来并非“完全没有 Bootloader”。**读到 0 不是立即允许覆写的证据**。

### 第三步：一次性恢复本机原厂 FIP

这一步使用的是已经验证来源、长度、校验值的**原机专属** 896KiB payload。诊断过程记录的一条关键操作形式如下（**不是可以复制执行的完整命令**）：

```text
tools/update partition bootloader <YOUR_OWN_VERIFIED_FIP_896KiB.PARTITION>
```

请注意：

- 这个命令对 eMMC **有实际写入副作用**；
- 现场还核对了工具版本、接口协议、目标分区与 ROM 启动位置；
- 没有来源可靠的本机 FIP、没有板级 mapping、不能验证写入位置，就不具备复制此操作的条件；
- **不要下载陌生人的 896KiB 文件尝试“套壳救砖”**。

### 第四步：两次独立读回验证

工具报告写入 `mwrite success` 后，我们没有直接宣布成功。

1. **命名分区读回**：`mread store bootloader normal 0xe0000`，与原机 FIP SHA256 逐字节相同。
2. **物理 eMMC 读回**：确认目标是该机器的 eMMC 用户区 LBA1，读取后续 **1792 个扇区**，与原机 FIP 原始数据完全一致。

当时用到的只读 U-Boot 诊断思路包括：

```text
mmc dev 1 0
mmc read 0x03000000 1 1792
```

**切勿照抄到别的机器**：`mmc 1`、RAM 地址 `0x03000000`、eMMC 代际及硬件布局可能不同；上面只是我们真实现场的**只读读回证据**，而非普适的恢复参数。

本机 896KiB FIP 校验：

```text
a71f38458400b77b487ff4270e47b21edb810f61a90a3fcc9290f1a9a72cc775
```

这不是供下载的公共引导镜像，只作为可审计的现场证据。

### 第五步：真实启动验收

后续通过断开 WorldCup/恢复正常电源启动确认：

- 机顶盒进入 Android 6.0.1（API 23）；
- `p211` 设备标识正确；
- `sys.boot_completed=1`；
- HDMI `1080p60hz`，以太网和授权 ADB 可用；
- 软重启后再次正常开机；
- 1080p H.264 原生播放链进入 PLAYING（具体边界见 [验收清单](04-验收与已知问题.md)）。

所以**本次救砖成功是有物理 FIP 读回 + Android 系统实际启动两层证据的**，不是把烧录进度条作为判断依据。

## 进入不了 WorldCup 怎么办？

可以做的低风险排查：

1. 断开其他 USB 外设，检查电源稳定、OTG 数据线和 Windows USB 枚举；
2. 检查设备管理器硬件 ID；如果进入 WorldCup，可能看到 **VID 1B8E / PID C003**（本机真实观察值）；
3. 若系统仍能启动，可以审查原 U-Boot 的 update 入口，但要先移除任何带自动烧录逻辑的 U 盘文件；
4. 无法进入时，结合**你的真实 PCB 修订号**找维修文档或使用可确认接线的救援工具。**本文不提供未经核验的 eMMC 短接点图。**

**不要**用禁用 Windows 驱动签名、盲刷陌生机器 Bootloader、全盘擦除等方式“碰碰运气”。

## 如何回到原厂 4.4.2？

如果已经做了完整、可读且校验过的**本机** 4.4.2 `boot`、`system`、`recovery`、DTB、原始引导、分区元数据备份，恢复时应严格按实际分区映射逐项回写并核验；也要特别检查用户数据与文件系统版本是否兼容。

本项目没有公开“把这台机器的备份烧进别的 E900V21C”的流程。**恢复必须用你的备份、你的目标映射、你的芯片和你自己的校验。**

---

## 一句话结论

**真正的救砖不是“另找一个包全量刷掉”，而是先搞清 BootROM 实际从哪里启动、哪一段数据被损坏、能否只恢复那一段，并通过真实字节读回和开机证明结果。**
